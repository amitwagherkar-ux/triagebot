How does it work?
A rapid 1-click triage desk for auditing AI recommendations, verifying evidence, and fixing mistakes
🎯 1. Purpose of the Queue
A rapid human-in-the-loop triage desk. Instead of combing through the full master table, analysts work through a card deck of tickets that require human judgment or where the AI made a mistake.
🃏 2. Anatomy of a Card
• Header: Jira link, Expected Ground Truth badge, and High Risk warning when confidence ≥ 80%.
• Left Box: AI Recommendation badge, confidence score %, and extracted reasoning.
• Right Box: Jira reality (actual developer action, assignee, priority).
⚡ 3. The 3 Fast Actions
• ✓ Correct: 1-click approval when AI is right; marks response quality as "Good" and logs the audit record.
• ✗ Override: Opens the full-screen Deep Dive Workstation to pick the true class and tag root cause errors.
• ⚡ Escalate: Flags ambiguous or missing-info tickets as Needs Manual Triage for engineering leads.
📊 4. Queue Filter Tabs
• Pending: Active tickets to audit. Reviewed tickets automatically leave this queue!
• Reviewed: Inspect all previously audited tickets (showing Status: Reviewed).

⚡ The 5 Rules
1. Start from expected behavior.
2. Do not rely on keywords (bug, issue).
3. Separate cause from fix method.
4. Use evidence.
5. Escalate uncertainty (Manual Triage).
💡 Pro-Tip
Consult the benchmark tickets below (e.g., EA-14523 PO numbers) to understand why symptoms can sound like defects but actually be configuration!

Authoritative Triage Decision Framework

Use these rules when reviewing borderline or ambiguous tickets. Keyword signals must never independently dictate classification.

Rule 1 — Start from Expected Behavior

Ask: "What is the product supposed to do?" Do not classify based solely on what the reporter calls the issue.

Rule 2 — Do Not Rely on Keywords

Words like bug, issue, enhancement, feature, error are signals only and never determine classification.

Rule 3 — Separate Cause from Fix Method

A DB query fix does NOT make it Config. Engineering work does NOT make it Change Request. Classification is based on the underlying behavior and specification.

Rule 4 & 5 — Use Evidence & Escalate Uncertainty

Prefer reproduction results and configuration checks. When evidence is conflicting or ambiguous, classify as Needs Manual Triage.

The Golden Principle: Always ask: "What is the product supposed to do today?" Never classify based only on what the requester calls the problem!

The 5 Authoritative Decision Rules

Rule 1 — Expected Behavior First

Identify what the system is intended to do today. If expected behavior cannot be established, do not infer it solely from ticket wording.

Rule 2 — Never Rely on Keywords

Words like bug, error, enhancement, issue, duplicate are surface signals only. They must never independently decide the class.

Rule 3 — Separate Cause from Fix Method

A DB query fix does NOT make an issue Config. Engineering involvement does NOT make it a Change Request. Classify on requirements.

Rule 4 & 5 — Use Evidence & Escalate

Prefer reproduction steps and config checks. If evidence is conflicting, low-confidence, or ambiguous, escalate to Needs Manual Triage.

Category Definition & Core Test First Practical Action Historical Benchmark Case

Why We Don't Rely on Basic Accuracy Alone: Simple accuracy can look high (e.g. 85%) while hiding that 100% of Configuration issues are being misclassified as Bugs, or that the bot is making dangerous high-confidence hallucinations!

Understanding the Key Metrics

Metric Formula What It Tells You
Attempted Accuracy Correct / (Correct + Incorrect) Accuracy specifically when the AI committed to a definitive triage decision (excluding abstentions).
Macro F1-Score Average(F1_Bug, F1_Config, F1_CR) Balanced metric giving equal weight to all classes. Prevents high Bug volume from hiding poor Config accuracy.
Precision TP / (TP + FP) When the AI predicts a class (e.g. Bug), how often is it actually that class? (Measures false alarm rate).
Recall TP / (TP + FN) Out of all actual tickets in a class, how many did the AI successfully catch? (Measures leak rate).
High-Risk Error Count Incorrect & Conf ≥ Threshold The count of tickets where the model was confident (≥ 80%) but wrong. Priority #1 for engineering fixes.

Audit Integrity Rule: A reviewer's override establishes the final ground truth for evaluation, but never erases the original AI output. Both are preserved side-by-side for audits.

The 3 Reviewer Actions Explained

1. [✓ Correct] (Fast Confirmation)

Confirms the AI classification is accurate. Updates the ticket status to Reviewed, increments correct counts, and marks the review card completed.

2. [✗ Override] (Detailed Correction)

Opens the Deep-Dive drawer. Requires selecting the Correct Classification, one of 14 Root-Cause Error Types, and rating response quality.

3. [⚡ Escalate] (Manual Triage)

Pulls uncertain tickets out of automation into human engineering triage. Removes high-risk false alarms from automated error counts.

The 14 Root-Cause Error Taxonomy Categories

Feedback Tag When to Select This Tag
Configuration mistaken for Bug AI called it a defect, but feature capability exists and issue is account setup or permission.
Change Request mistaken for Bug AI mistook user's request for new behavior or validation as an existing code defect.
Bug mistaken for Config AI assumed user had wrong settings, but existing software behavior was genuinely broken.
Expected behavior misunderstood AI misread the product specification or intended workflow rules.
Unsupported assumption AI hallucinated facts (e.g. claimed a permission was disabled when no Jira evidence existed).
Insufficient evidence Ticket lacked logs/reproduction details, but AI forced a guess instead of escalating.
Recommended action incorrect Classification was correct, but suggested next step was invalid or counter-productive.
Suggested owner incorrect AI routed ticket to the wrong team based on available Jira metadata.

How to Train & Improve the Model by Adding More Jira Tickets: Training an LLM triage bot isn't just about throwing thousands of random tickets at it—it is about finding tricky edge cases, capturing human corrections, and feeding those lessons back into your prompt.

The 6-Step Efficient Training Loop

Step 1
1. Export Diverse Tickets
Gather 30–50 fresh Jira tickets across different modules (CRM, Inventory, Billing, Interfaces). Include tickets that were resolved via DB query or configuration to test edge cases.
Step 2
2. Batch Predict with AI
Run your LLM over the batch. Output the 6 core fields formatted per SAMPLE_IMPORT_TEMPLATE.csv (Ticket ID, AI Classification, Confidence, Reason, Evidence, Next Action).
Step 3
3. Ingest into the Tool
Go to + Ingest AI Run. Upload the file, confirm the auto-matched columns, assign a clear tag (e.g. Claude 3.5 - Sprint 42), and validate.
Step 4
4. Human Review & Tagging
Open the Review. Click [✗ Override] on mistakes, assign the true classification, tag the root cause (e.g. Configuration mistaken for Bug), and write a quick reason.
Step 5
5. Export Error Report
Go to Export Center → Download Error Report CSV. This is your "Mistake Notebook" containing all high-value edge cases with reviewer explanations.
Step 6
6. Update Prompt / Fine-Tune
Add the top 5–10 confused tickets as Few-Shot Examples in your system prompt. Re-run your bot, ingest as Run B, and use Model Comparison to verify accuracy gains!

Why This Training Strategy Works

• Eliminates Keyword Blindspots: LLMs naturally latch onto words like "duplicate" or "error". Teaching the model with real historical tickets (like EA-14523 where duplicate PO numbers were actually center configuration) permanently cures false positive bugs.
• Measurable Progress: In the Model Comparison tab, the Shift Analysis immediately shows which tickets were cured (Fixed) vs which got broken (Regressed), guaranteeing you never ship a regression to production!
